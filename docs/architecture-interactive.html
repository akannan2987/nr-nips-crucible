🏗️ The four layers of Pandora

Like floors in a building — each layer has one clear job.

🎨

Layer 1 · Presentation (Client)

What the user sees and interacts with

A React 18 Single Page Application bundled by Vite and styled with Tailwind CSS. It runs entirely in the user's browser — no server-side rendering.

  • Dashboard — summary cards showing record counts, recent activity, and system health.
  • ELN (Electronic Lab Notebook) — upload forms for Chemicals, Samples, Screening, and Toxicology. Supports manual entry, Excel bulk upload, and SDF chemical structure files.
  • Viewer — paginated data tables with search, sort, inline editing, bulk select/delete, and molecular structure preview.
  • React Router handles navigation without page reloads; Axios handles all HTTP calls; React Hot Toast provides user feedback.
client/src
🔀

Layer 2 · API Gateway (Server Routes)

The traffic controller & request dispatcher

A FastAPI application (served by uvicorn) exposing RESTful endpoints on port 49160. Each route maps to a specific resource and operation — one router file per resource.

  • GET/POST/PUT/DELETE /api/chemicals — CRUD operations for chemical records.
  • POST /api/chemicals/upload/excel — bulk import from Excel via UploadFile + openpyxl.
  • GET/POST /api/samples, /api/screening, /api/toxicology — similar patterns for other collections.
  • GET /api/stats — health check and record counts (used by the container healthcheck and monitoring cron).
  • External API proxy: can call PubChem or LabKey to enrich or sync data without exposing credentials to the frontend.
  • Also serves the compiled React static files (HTML/JS/CSS) so only one port is needed — plus free interactive API docs at /docs.
backend/app/routers
🧠

Layer 3 · Business Logic (Middleware & Handlers)

The brain — validation, transformation & rules

Code that runs between receiving the request and writing to the database. This is where domain rules live.

  • Input validation: required fields, format checks (CAS regex, molecular formula patterns), duplicate ID detection.
  • File parsing: openpyxl reads Excel rows (including the SLIMS 3-row header); the RDKit-backed SDF module handles V2000 + V3000 molfiles, S-Groups (polymer/mixture detection), atom charges & stereo, and preserves every regulatory field (EPA DSSTox, EU FCM, US 21 CFR, Nestlé SBL) verbatim in metadata.
  • External enrichment: calls PubChem REST API to auto-fill formula, MW, SMILES, InChIKey from a CAS number or name.
  • Capacity enforcement: rejects inserts that would exceed the ~50K performance threshold.
  • Bulk operations: batch insert/update/delete with per-row error tracking and summary reports.
  • Error handling: catches exceptions and returns user-friendly JSON errors without leaking stack traces.
in route handlers
💾

Layer 4 · Data Persistence (Storage)

The memory — where records live

SQLite stores all data in a single file (data/crucible.db), accessed through the SQLAlchemy 2 ORM. Replaced the v1 JSON file store in v2.0.

  • 4 tables: chemicals, samples, screening, toxicology — linked via chemical_id (1:many, by convention).
  • Hybrid document pattern: each row keeps the full record verbatim in a JSON doc column + indexed lookup columns, so API responses stayed identical to the v1 era.
  • File-based: backup = copy the file; restore = replace it. No database server to manage.
  • Persistence: data/ mounted as a host volume in Podman/Docker so data survives container rebuilds and restarts.
  • PostgreSQL (optional): change DATABASE_URL (the doc column maps to JSONB natively); Alembic owns the schema in the container.

🧰 The toolbox behind the Toolbox

Every piece chosen to be modern, lightweight, and easy to maintain. Here's what each does and why it was picked.

🎨 Frontend

⚛️React 18 ▶ click

Component-based UI framework from Meta. Chosen for its huge ecosystem, declarative rendering, and virtual DOM that makes updates fast without full page reloads. Industry standard for SPAs.

🤔 Why React over alternatives?

OptionVerdict
Vue.jsGreat framework, but smaller talent pool at Nestlé. React devs are easier to find and onboard.
AngularFull framework with TypeScript, DI, RxJS — too heavy and opinionated for a small internal tool.
SvelteInnovative compiler approach, but immature ecosystem. Fewer UI component libraries available.
Vanilla JSNo templating, no state management, no component reuse. Maintenance nightmare at scale.

Winner: React — largest ecosystem (thousands of ready-made components), virtual DOM for fast updates, hooks for clean state management, and universal developer familiarity.

⚡Vite ▶ click

Next-gen build tool with instant hot module replacement (HMR) during development and optimized production bundles. 10-100× faster than Webpack. Zero-config for React projects.

🤔 Why Vite over alternatives?

OptionVerdict
WebpackIndustry workhorse but slow cold starts (10-30s), complex config files, and plugin hell.
Create React AppDeprecated. Uses Webpack under the hood. Slow, bloated, no longer maintained.
ParcelZero-config like Vite but slower and less ecosystem adoption.
TurbopackStill in beta (Next.js only). Not production-ready for standalone React apps.

Winner: Vite — native ES modules for instant dev server startup, Rollup-based production builds, and the new standard for React/Vue/Svelte projects.

🌬️Tailwind CSS ▶ click

Utility-first CSS framework. No custom CSS files needed — styling lives directly in JSX. Produces tiny production bundles via tree-shaking. Consistent design system out of the box.

🤔 Why Tailwind over alternatives?

OptionVerdict
BootstrapPre-built components but opinionated look. Hard to customize without fighting the framework.
Plain CSS / SCSSFull control but no consistency. Naming conventions (BEM) add overhead. Grows messy over time.
CSS ModulesScoped styles but still need to write CSS from scratch. No design system included.
Styled ComponentsCSS-in-JS adds runtime cost. Larger bundle size and debugging is harder.

Winner: Tailwind — co-located styling (no context switching), automatic tree-shaking (only ships used classes), responsive design built-in, and consistent spacing/color system.

🧭React Router ▶ click

Client-side routing for SPA navigation. Enables URL-based views (e.g., /chemicals, /samples) without page reloads. Supports nested routes and lazy-loading.

🤔 Why React Router?

OptionVerdict
TanStack RouterType-safe and modern, but newer with smaller community. Migration docs are sparse.
WouterTiny (~1KB) but lacks nested routes, loaders, and lazy-loading support.
No router (manual)Conditional rendering works for 2 pages, not for 6+ views with deep links and browser back/forward.

Winner: React Router — de facto standard for React SPAs, supports lazy loading, nested layouts, URL params, and has 10+ years of stability.

📡Axios ▶ click

Promise-based HTTP client with interceptors, automatic JSON parsing, and request/response transforms. Cleaner API than fetch() with built-in error handling and timeout support.

🤔 Why Axios over fetch()?

OptionVerdict
Native fetch()Built-in but no interceptors, no timeout, no automatic JSON parsing, doesn't reject on 4xx/5xx status.
kyModern fetch wrapper but smaller community. Less documentation and examples.
Got / node-fetchServer-side only. Don't work in browsers.

Winner: Axios — request/response interceptors (for error handling), automatic JSON, timeout support, works in both browser and Node.js, and cancellation via AbortController.

🔔React Hot Toast ▶ click

Lightweight toast notification library (~5KB). Shows success/error/loading messages without blocking the UI. Customizable, accessible, and auto-dismisses.

🤔 Why React Hot Toast?

OptionVerdict
React ToastifyFeature-rich but heavier (~30KB). More config needed for simple use cases.
NotistackMaterial UI dependency. Overkill if not using MUI.
Custom solutionReinventing the wheel. Accessibility, animations, stacking — non-trivial to build correctly.

Winner: React Hot Toast — ~5KB, zero dependencies, beautiful defaults, promise-based API (toast.promise()), and accessible out of the box.

⚙️ Backend

🐍Python 3.12 ▶ click

Backend runtime (python:3.12-slim container). Chosen for the v2.0 rewrite: the maintainer's primary language, and home turf for scientific tooling — RDKit, pandas, openpyxl are all Python-native.

🤔 Why Python over staying on Node.js?

OptionVerdict
Node.js (previous stack)Worked, but the sole maintainer is a Python developer; JS expertise was the bottleneck for every change. Retired after the migration.
Go / JavaFast, but no RDKit, and a steeper curve for an intermediate Python maintainer.

Winner: Python — maintainability by the actual team, first-class chemistry libraries (RDKit), and type hints + Pydantic give the API a safety net JavaScript never had. Migrated strangler-fig style with parity tests so the React client never noticed.

⚡FastAPI + uvicorn ▶ click for details

Modern Python web framework (backend/app/). Declarative routes, dependency injection, Pydantic validation, and free interactive API docs at /docs. Served by uvicorn on port 49160 — same endpoints, same responses as the v1 API it replaced.

🤔 Why FastAPI over alternatives?

OptionVerdict
FlaskSimple, but validation, typing, and OpenAPI docs are all add-ons. FastAPI has them built in.
Django / DRFFull-stack framework with its own ORM, admin, and conventions — heavy for a REST API with an existing React frontend.
aiohttp / Starlette rawLower-level; more boilerplate for routing, validation, and docs.

Winner: FastAPI — type-hint-driven (parameters parse and document themselves), Pydantic request models, and an OpenAPI UI for free. One router file per resource keeps the code easy to navigate.

⚠️ React alone is NOT enough. React runs in the browser — it cannot read/write files, store persistent data, or handle uploads securely. A backend (FastAPI here) is mandatory.

🗄️SQLite + SQLAlchemy 2 ▶ click

A real database in a single file (data/crucible.db), accessed through the SQLAlchemy ORM. Replaced the v1 JSON file store. Backup is a single-file snapshot (./container-py.sh backup).

🤔 Why SQLite (and how the schemaless data fits)?

OptionVerdict
Keep LowDB JSONWhole file rewritten on every change; no indexes or transactions; JS-only tooling.
PostgreSQL nowNeeds a running server on the VM — extra ops for <50K records. Kept as the upgrade path: switching is a DATABASE_URL change.
MongoDBDocument fit is fine, but a daemon + memory footprint for a single-user lab app is overkill.

Winner: SQLite — zero-ops, transactional, and Python-native. Each table uses a hybrid document pattern: the full record lives verbatim in a JSON doc column (so API responses stayed byte-identical to the v1 era), plus indexed columns (id, business key, created_at, insertion order) for lookups.

📂FastAPI UploadFile ▶ click

File uploads (Excel/SDF) are handled by FastAPI's built-in UploadFile (powered by python-multipart) — the same multipart/form-data field name (file) as the v1 upload setup, so the React upload pages work unchanged.

🤔 Why UploadFile?

No separate middleware needed: declare file: UploadFile = File(...) in the route signature and FastAPI parses the multipart body, streams big files to a spooled temp file, and hands over bytes with await file.read(). A missing file returns the same 400 {"error": "No file uploaded"} the v1 API produced.

📊openpyxl ▶ click

The standard Python Excel reader (backend/app/utils/excel.py). Parses .xlsx uploads — including the SLIMS sample export with its unusual 3-row header — plus a small RFC-4180 CSV parser that keeps CAS numbers like 58-08-2 as text instead of mangling them into dates.

🤔 Why openpyxl?

OptionVerdict
pandas.read_excelAvailable (pandas is installed), but it type-coerces cells aggressively; the SLIMS parser needs raw, string-faithful cell access. pandas uses openpyxl underneath anyway.
xlrdDropped .xlsx support years ago; legacy .xls only.

Winner: openpyxl — faithful cell-level control, mirroring the v1 raw:false cell behaviour so uploaded values land in the database formatted exactly as before.

🧬RDKit (SDF handling) ▶ click

The industry-standard chemistry toolkit powers SDF ingestion (backend/app/utils/sdf.py), replacing the in-house JS parser. Hybrid design: record text (MOL block + every > <FIELD> item) is preserved verbatim; RDKit supplies the structural intelligence — formula/weight, S-Groups (SRU/MUL/COP → polymer detection), charges, radicals, stereo, mixtures.

🤔 Why RDKit now (vs the custom JS parser)?

OptionVerdict
Port the JS parser line-by-line850 lines of hand-rolled V2000/V3000 parsing to maintain forever; RDKit does it better and is battle-tested.
RDKit alone (no text layer)Would normalize the MOL block and could drop vendor regulatory fields — the app must keep them verbatim.

Same 3-tier extraction contract as before

  • Tier 1 — Named fields: dtxsid, preferred_name, monoisotopic_mass, ms_ready_smiles, synonyms[], CAS, InChI, SMILES (50+ aliases, case-insensitive — mapping tables ported verbatim).
  • Tier 2 — Catch-all: every other > <FIELD> kept in metadata (EU FCM code, US 21 CFR, Nestlé SBL, ADI/TDI, SML, …) — parsed textually, nothing dropped.
  • Tier 3 — Structural intelligence: derived structural{} object: isPolymer, polymerLabels[], isMixture, componentCount, hasStereochemistry, totalCharge, sGroupTypes[] — now computed by RDKit.

Winner: hybrid RDKit — pip-installable wheel (macOS arm64 + linux x86_64), professional-grade chemistry, and lossless regulatory metadata.

🆔UUID ▶ click

Generates universally unique identifiers (v4) for every record. Guarantees no collisions even across distributed systems. No auto-increment counter needed.

🤔 Why UUID over auto-increment?

OptionVerdict
Auto-increment (1,2,3…)Requires centralized counter. Breaks during bulk imports, merges, or distributed writes.
nanoidShorter IDs but less universally recognized. UUID is a standard (RFC 4122).
Timestamp-basedCollisions if two records created in the same millisecond.

Winner: UUID v4 — cryptographically random, zero collision risk, no coordination needed, and universally understood across all systems.

🌐PubChem REST API ▶ click

Free NIH chemical database (100M+ compounds). Used to auto-fill molecular formula, weight, SMILES, and InChIKey from a CAS number or compound name. Eliminates manual data entry errors.

🤔 Why PubChem?

OptionVerdict
ChemSpiderRequires API key registration. Smaller database. Rate limits are stricter.
ChEBIFocused on biological chemicals only. Smaller coverage for food/pharma compounds.
Local databaseWould need regular updates. 100M+ compounds = massive storage. Maintenance burden.
Manual entryError-prone. Scientists shouldn't type molecular formulas by hand.

Winner: PubChem — free, no API key required, 100M+ compounds, fast REST API (~200ms), returns formula/MW/SMILES/InChIKey/IUPAC name in one call.

🔗LabKey Server API ▶ click

Nestlé's enterprise LIMS platform. Integration allows syncing samples and experiment metadata between Pandora and the central LabKey instance. Future-proofs data sharing.

🤔 Why LabKey integration?

LabKey is Nestlé's existing enterprise LIMS (Laboratory Information Management System). Pandora doesn't replace it — it complements it:

  • Pandora = fast, lightweight tool for daily chemical/sample management by individual scientists.
  • LabKey = enterprise system of record for cross-team data sharing, compliance, and auditing.
  • Integration allows pushing validated Pandora records into LabKey for long-term archival and sharing.
  • Avoids double data entry — enter once in Pandora, sync to LabKey automatically.

🚀 Delivery & Ops

📦Podman (Docker-compatible) ▶ click

Rootless container engine. Packages the entire app (Node, React build, certs) into one portable image. Identical behavior on dev and production. No "works on my machine" issues. Chosen over Docker for daemonless, rootless security.

🤔 Why Podman over Docker?

OptionVerdict
DockerRequires a daemon running as root. Security risk on shared servers. Licensing concerns for enterprise.
Bare metal (no container)Works but "it works on my machine" issues. No isolation, dependency conflicts with other apps on the server.
KubernetesMassive overkill for a single-container app. Adds operational complexity without benefit here.

Winner: Podman — daemonless (no root process), rootless containers (security), Docker-compatible CLI (same commands), and already approved on Nestlé's infrastructure.

🔒HTTPS / TLS 1.3 ▶ click

End-to-end encryption using Nestlé's official SSL certificates. Protects chemical data and user sessions in transit. Required for corporate network compliance and browser trust.

🤔 Why HTTPS at the app level?

OptionVerdict
Reverse proxy (Nginx)Common pattern but adds another component to manage. Single container is simpler.
HTTP onlyBrowsers show "Not Secure" warning. Corporate policy forbids unencrypted traffic.
Let's EncryptGreat for public sites but Pandora is internal-only. Nestlé has its own CA.

Status in v2.0: the Python backend serves TLS in-process via uvicorn with Nestlé's certificates — start it with ./container-py.sh start-ssl (falls back to HTTP when no certs are present). See DEPLOYMENT.md → SSL/TLS.

⏰Cron + monitor.sh ▶ click

System cron job runs every 5 minutes. Hits the /api/stats health endpoint; if it fails, automatically restarts the container. Simple, reliable, zero-dependency monitoring.

🤔 Why cron over monitoring tools?

OptionVerdict
Prometheus + GrafanaPowerful but requires deploying 2 extra services. Overkill for one container.
systemd watchdogGood but Podman containers aren't systemd services by default. Extra config needed.
No monitoringApp crashes silently. Nobody notices until a user reports it hours later.

Winner: cron + shell script — zero dependencies, works on any Linux, 5 lines of bash, and has been reliable for decades. KISS principle.

📈Auto-restart & Self-healing ▶ click

Podman's --restart=always policy + the cron monitor ensure the app recovers from crashes, OOM kills, or host reboots automatically. Zero manual intervention needed.

🤔 Why self-healing matters

Without auto-restart, a single crash at 2 AM means the app is down until someone manually intervenes the next morning. With the dual-layer approach:

  • Layer 1: Podman's --restart=always handles immediate crashes (process exit, OOM kill).
  • Layer 2: Cron monitor catches "zombie" states where the process is alive but unresponsive (hung connections, deadlocks).
  • Result: Maximum downtime ≈ 5 minutes (one cron cycle). No pager, no manual SSH needed.

💡 Why this particular stack?

🎯 Simplicity

One single-file database (SQLite). One container for deployment. A backend in the maintainer's primary language (Python). Minimal moving parts = minimal failure points.

🚀 Speed of development

React + Vite hot reload, FastAPI's declarative routes with auto-docs, SQLite zero-config. A new feature can go from idea to production in hours, not weeks.

📦 Portability

The entire app runs in a single container. Move it to any Linux server with Podman/Docker and it works identically. No database server, no cloud dependencies.
